# 0019. Invite expiry runs hourly, from a Lambda bundled in the package

- **Status:** Accepted, 2026-10-17; amended 2026-10-18 (never the last owner, below)
- **Standard:** 03 §2 Roles and lifecycle ("An invite with no sign-in after 7 days is disabled"; "keep an owner")

## Context

An invite is a live account from the moment it's created: anyone who controls that inbox can sign in with an emailed code. auth-kit had the sweep (`createInviteExpirySweep`: disable every unaccepted invite older than 7 days, remove its admin roles, log each as intent → calls → result) and the README said "schedule it daily", but nothing scheduled it. The 2026-10-17 demo sent a real invite saying it expired on a date nothing enforced.

## Decision

- **`InviteExpirySweep`** in `auth-kit/admin/cdk`, next to `AuditLogTable`: EventBridge Scheduler, in a schedule group of its own, invokes a Lambda function that runs the sweep as `system:invite-expiry` (the Activity page shows "Scheduled job").
- **Hourly by default**, so an unused invite is disabled within an hour of its seventh day. A `rate` between 10 minutes and a day, or a `cron`, can replace it; anything slower is refused. Each run costs one `ListUsers` page per 60 accounts, spent against auth-kit's share of the account's Cognito quota.
- **Least privilege.** The function's role may make `ListUsers`, `AdminListGroupsForUser`, `ListUsersInGroup` (the owner count, below), `AdminDisableUser`, and `AdminRemoveUserFromGroup` on its pool, `PutItem` on the audit table (`AuditLogTable.grantAppend`: no reads, no edits), and write its own log group; no managed policies. The scheduler's role may only invoke that function, and only this account's scheduler, for this group's schedules, can assume it. `inviteExpirySweepPolicy` gives the same function permissions as plain JSON.
- **Failures are loud.** A run that couldn't disable a due invite, or that stopped at `maxPeople` (default 5000), logs what it did and then fails, so the function's errors metric counts it. With `alarmTopic`, two alarms: a failed run, and an invocation the scheduler dropped. No retries inside a run's slot beyond the scheduler's delivery retries; the next run sweeps again.
- **The function's code ships in the tarball.** `npm run build` also bundles the handler with every dependency, the AWS SDK clients included, into `dist/lambda/invite-expiry/index.mjs` (about 0.9 MB, unminified so stack traces read). The construct deploys that file. Sites don't need esbuild at synthesis, and the function runs exactly the code [0012](0012-release-tarballs.md) attests, not whatever SDK the Lambda runtime has that day. To keep the bundle free of Next.js and React, the sweep lives in its own module (`src/admin/sweep.ts`), not in the People actions.

## Consequences

- One more stack resource set per site (a function, two roles, a schedule and its group, a log group kept three months), all near zero cost.
- Sandboxes get the sweep too. Seeded personas have verified addresses, so it never disables them.
- Raising `maxPeople` past what five minutes of quota-limited `ListUsers` allows needs a longer timeout; at 5000 accounts a run takes well under a minute.

## Amendment, 2026-10-18: never the last owner

David's decision. A site's first owner is usually created by hand and may not sign in for a week; the sweep as first written would then disable them and strip the owner role, leaving a site with no owner and only the break-glass path back in. The People actions already refuse to remove the last owner; the sweep didn't.

- **The rule.** The sweep never disables, or removes roles from, the site's last owner: the last enabled holder of the owner role, even one who never signed in. The owner role is `OWNER_GROUP` in `src/shared/policy.ts` (today `superadmin`, "Owner" on screens); the sweep never names the group itself, so a change to which group is the owner changes only that constant. A non-last owner who is disabled loses the owner group and every admin role. Before disabling an expired owner invite it reads the owners live (`ListUsersInGroup`, once per due owner, so a concurrent change has the smallest window) and disables only if another enabled owner remains, not counting the person themselves or anyone this run tried to disable, whatever that attempt's outcome. So two owners with one unused invite: the unused one is disabled. Two owners, both unused and expired: one is disabled, one kept. Non-owner invites expire as before.
- **Fail closed, toward keeping the owner.** If the owner list can't be read, the owner is skipped (a `refused` row with `owner_count_unknown`) and the run reports a failure, so the alarm fires and the next run retries. If a due invite's own groups can't be read, there's no telling whether they're the last owner, so they're skipped and reported too. (Before, an unreadable group list was treated as no groups: the account was disabled and kept its roles.) This costs at most an hour of a still-open invite, with an alarm, against an ownerless site.
- **Skipped, logged, warned.** A skipped last owner gets a `refused` audit row (`people.expireInvite`, `error: "last_owner: skipped: last owner. …"`, the warning sends in `calls`), shown on the Activity page as "Scheduled job tried to disable the unused invite for …, refused". The owner gets "Your owner invite to {Site} hasn't been used" and, in a message of its own (so a mistyped owner address, a likely reason the invite went unused, can't stop it), an optional fallback address gets a copy naming the owner. Both go through the mailer (`OwnerInviteWarningNotifier.ownerInviteUnused`; `createSesInviteMailer` implements it). The construct's `ownerWarnings` prop sets the site name, sender, sign-in URL, fallback, and configuration set, and grants `ses:SendEmail` from that identity only (default: the sender's domain).
- **Once a day, without reading the log.** The function's role still never reads the audit log, so it can't look up when it last warned. Instead the construct tells it how often it runs (`AUTH_KIT_RUN_EVERY_MINUTES`, from a `rate` schedule), and it warns, and writes the refusal row, on the first run after the invite expired and on the first run of each day after that (`lastOwnerWarningDue`). The runs in between still skip, and list the skip in their log line. With a `cron` the interval is unknown, so every skipping run warns: use a daily `cron` or a `rate`. An admin's `people.expireStaleInvites()` warns on every run, through the People mailer.
- **What fails a run.** A skip that warned and logged is the steady state, not a failure. A skip that couldn't warn anyone (no `ownerWarnings`, or SES refused) or couldn't write its row fails the run, so with `alarmTopic` someone hears about it even with no warning configured. The log line redacts any address an AWS error message quotes.

Considered: granting the function `Query` on the audit table to find its last warning. That would let a role that today only appends read every row (reasons, admins' addresses and IPs); IAM's `dynamodb:LeadingKeys` isn't documented for index partitions, so it couldn't be narrowed to the sweep's own rows. A deterministic once-a-day window keeps the role write-only, at the cost of a rare doubled or missed day when a run's start time drifts across the window's edge.
